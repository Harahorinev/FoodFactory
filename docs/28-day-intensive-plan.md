# 28-дневный интенсив по 1С на проекте FoodFactory

## Рамки плана

- Стартовая точка: Senior React/TypeScript-разработчик с 8-летним опытом, начинающий изучать 1С с нуля.
- Среда: Mac M3 Pro, учебная платформа 1С:Предприятие 8.3.27.1688, файловая информационная база `FoodFactory`.
- Дни 1–4 завершены. Следующий — день 5. Подробности выполнения — в `PROGRESS.md`.
- Нагрузка: 195 продуктивных часов за 28 дней. Это внутри допустимого бюджета 168–224 часа и целевого диапазона 180–200 часов.
- Ритм: для уже завершённого дня 1 в бюджете зарезервировано 6 часов (фактическая длительность в `PROGRESS.md` не зафиксирована); дни 2–28 — по 7 часов. В каждом дне предусмотрены короткие перерывы сверх указанного продуктивного времени.
- Под «самостоятельной практикой» понимается постановка без готового кода. Сначала следует реализовать решение самостоятельно, затем показывать наставнику метаданные, модуль и результат проверки.
- Все названные ниже объекты — **учебные метаданные, создаваемые в конфигурации FoodFactory**. Это не утверждение о наличии таких объектов в какой-либо типовой конфигурации 1С.
- Названия новых объектов предварительные: перед созданием нужно сверять, нет ли в учебной конфигурации уже созданного объекта с тем же назначением.

## Сквозная модель FoodFactory

К концу интенсива учебная конфигурация должна поддерживать упрощённый контур:

1. учёт учебной номенклатуры и складов;
2. приход сырья;
3. рецептуры;
4. выпуск готовой продукции и списание сырья;
5. отгрузку покупателю;
6. остатки, обороты и себестоимость в упрощённой учебной модели;
7. отчёты, разграничение доступа и безопасное расширение.

Планируемые учебные объекты:

- подсистемы: существующая `Склад`; новые `Производство`, `Продажи`, `Администрирование`;
- справочники: существующий `Номенклатура`; новые `ЕдиницыИзмерения`, `Склады`, `Контрагенты`, `Рецептуры`;
- перечисление `ВидыНоменклатуры`;
- документы `ПриходСырья`, `ВыпускПродукции`, `РеализацияПродукции`;
- регистры накопления `ОстаткиНоменклатуры`, `ЗатратыНоменклатуры`, `Продажи`;
- регистр сведений `СоставРецептур`;
- отчёты `ОстаткиНаСкладах`, `ПродажиИВаловаяПрибыль`, `ПланФактРасходаСырья`;
- обработки `УчебнаяПроверкаДанных`, `УчебныеСценарииПроверки`;
- роли `КладовщикFoodFactory`, `МастерПроизводстваFoodFactory`, `МенеджерПродажFoodFactory`, `АдминистраторFoodFactory`;
- расширение `FoodFactoryБезопасныеДоработки`.

Окончательные измерения, ресурсы, реквизиты и связи вводятся в соответствующий день после моделирования, а не создаются все заранее.

## Неделя 1. Язык, модули и модель метаданных

### День 1 — платформа и первый справочник (6 ч, завершён)

**Цель.** Зафиксировать уже пройденную стартовую точку; новых занятий сегодня нет.

**Ключевые концепции и аналогии.**

- Платформа — runtime и framework; конфигурация — исходная схема приложения; информационная база — развёрнутый экземпляр с данными.
- Конфигуратор близок к IDE и schema designer, режим 1С:Предприятие — к запущенному приложению.
- Подсистема — функциональная группировка и навигация, а не поле данных и не роль доступа.
- Справочник близок к агрегату ORM с автоматически предоставленными формами и ссылочной идентичностью.

**Метаданные/артефакт FoodFactory.** Уже созданы файловая база `FoodFactory`, подсистема `Склад`, справочник `Номенклатура` с реквизитами `Артикул` и `ЕдиницаИзмерения`; введён элемент «Мука пшеничная».

**Самостоятельная практика.** Завершена: создание базы, метаданных, обновление конфигурации базы данных и проверка сохранности элемента после повторного входа.

**Критерии готовности.** Подтверждены в `PROGRESS.md`: объект виден в интерфейсе, данные сохраняются, различие между подсистемой, полем, навигацией и правами понято.

### День 2 — основы встроенного языка (7 ч, завершён)

**Цель.** Научиться читать и писать небольшой безопасный код 1С без переноса синтаксических привычек TypeScript один к одному.

**Ключевые концепции и аналогии.**

- Значения, переменные без статической аннотации, `Неопределено`, `Null`, `Истина/Ложь`; отличие от `undefined`/`null` в TS.
- `Если`, `Для`, `Для каждого`, `Пока`, процедуры и функции; экспорт как публичный API модуля.
- `Структура`, `Массив`, `Соответствие`, `ТаблицаЗначений` как динамические аналоги object, Array, Map и in-memory table.
- Строки, даты, числа и особенности неявных преобразований: проверять типы явно там, где ошибка бизнес-логики опасна.

**Метаданные/артефакт FoodFactory.** Учебный общий модуль `УтилитыFoodFactory`; первые чистые функции нормализации артикула и пересчёта количества между учебными коэффициентами.

**Самостоятельная практика.** Самостоятельно написать функции, которые принимают набор строковых артикулов, удаляют пустые значения, нормализуют регистр, находят дубли и возвращают структурированный результат.

**Критерии готовности.** Код проходит синтаксическую проверку; корректно обрабатывает пустую строку, `Неопределено`, дубль и кириллицу; функции не меняют входную коллекцию; результат объяснён построчно.

### День 3 — процедуры, модули, ошибки и контракты (7 ч, завершён)

**Цель.** Разделять ответственность между модулями и проектировать небольшой API на встроенном языке.

**Ключевые концепции и аналогии.**

- Общие модули, модуль объекта, модуль менеджера и модуль формы: ближе к service module, entity hooks, static repository API и UI controller в Node/ORM.
- Области, экспортные процедуры, параметры по значению, соглашения об именовании.
- `Попытка/Исключение`, `ОписаниеОшибки()`, вызов исключения; аналог try/catch, но бизнес-ошибки не следует молча поглощать.
- Контракт функции: предусловия, постусловия и минимизация побочных эффектов.

**Метаданные/артефакт FoodFactory.** Общий модуль `ПроверкиFoodFactory`; модуль менеджера учебного справочника `Номенклатура`; текстовое описание публичных процедур обоих модулей.

**Самостоятельная практика.** Реализовать проверку корректности артикула и поиск элемента по артикулу так, чтобы UI-код не содержал логику поиска. Предусмотреть понятные диагностические сообщения, не выдавая пользователю внутренний стек.

**Критерии готовности.** Можно обосновать место каждой процедуры; экспортированы только нужные методы; ошибки не скрываются; четыре граничных случая проверены вручную.

### День 4 — управляемые формы и клиент-сервер (7 ч, завершён)

**Цель.** Понять границу тонкого клиента и сервера и не создавать «болтливый» интерфейс.

**Ключевые концепции и аналогии.**

- Модуль управляемой формы как frontend controller, серверный общий модуль как backend service.
- Директивы компиляции `&НаКлиенте`, `&НаСервере`, `&НаСервереБезКонтекста`; сериализуемые значения между слоями как DTO.
- Контекст формы и серверный контекст; почему ссылка на объект и объект данных не взаимозаменяемы.
- Один пакетный серверный вызов вместо цикла запросов — аналог устранения N+1 API calls.

**Метаданные/артефакт FoodFactory.** Учебная управляемая форма элемента `Номенклатура`; общий модуль `СервисНоменклатурыFoodFactory` с явно настроенными клиентскими/серверными свойствами.

**Самостоятельная практика.** Добавить команду формы, которая одним серверным вызовом проверяет уникальность артикула и возвращает DTO с результатом и пользовательским сообщением.

**Критерии готовности.** Пользовательский сценарий работает в режиме 1С:Предприятие; в цикле нет серверных вызовов; ученик может назвать место исполнения каждой строки; служебная логика не дублируется в форме.

### День 5 — справочники и ссылочная модель (7 ч)

**Цель.** Перевести строковые атрибуты в нормализованные учебные метаданные и освоить ссылки.

**Ключевые концепции и аналогии.**

- Ссылка, объект, представление, пустая ссылка; аналог foreign key и ORM reference, но с платформенным поведением.
- Предопределённые данные не вводятся автоматически без явной необходимости.
- Реквизиты, табличные части, владельцы и иерархия: выбирать по предметной семантике, а не ради тренировки.
- Ссылочная целостность и поиск ссылок перед опасным удалением.

**Метаданные/артефакт FoodFactory.** Учебные справочники `ЕдиницыИзмерения`, `Склады`; перечисление `ВидыНоменклатуры`; изменение реквизита `ЕдиницаИзмерения` справочника `Номенклатура` со строки на ссылку после ручного плана миграции учебных данных; новый реквизит `ВидНоменклатуры`.

**Самостоятельная практика.** Спроектировать и выполнить миграцию существующей «Муки пшеничной», не потеряв значение единицы; добавить минимум по два вида сырья и готовой продукции и два склада.

**Критерии готовности.** В `Номенклатура` нет дублирующихся строковых единиц; пустые ссылки обработаны; существующий элемент сохранён корректно; схема и причины типов объяснены через SQL/ORM.

### День 6 — язык запросов 1С: первые выборки (7 ч)

**Цель.** Получать данные запросом и не подменять запрос перебором всех объектов во встроенном языке.

**Ключевые концепции и аналогии.**

- `ВЫБРАТЬ`, `ИЗ`, `ГДЕ`, параметры, псевдонимы, сортировка и группировка; сходство с SQL и отличия языка запросов 1С.
- Ссылочные поля и обращение через точку; не считать это бесплатным ORM eager loading.
- `Запрос`, `УстановитьПараметр`, `Выполнить`, выборка и выгрузка в таблицу значений.
- Параметры вместо конкатенации текста запроса.

**Метаданные/артефакт FoodFactory.** Экспортная серверная функция `ПодобратьНоменклатуру` в `СервисНоменклатурыFoodFactory`; сохранённый учебный набор из пяти проверочных сценариев запроса в описании модуля.

**Самостоятельная практика.** Построить параметризованный поиск номенклатуры по виду, единице и фрагменту наименования с необязательными фильтрами; сравнить с наивным перебором.

**Критерии готовности.** Нет конкатенации пользовательского ввода в запрос; результат верен при пустом результате и пустых фильтрах; поля выбираются явно; ученик объясняет серверное исполнение.

### День 7 — контрольная точка 1 и буфер (7 ч)

**Цель.** Закрепить язык, модули, формы, ссылки и запросы; устранить пробелы без расширения предметной области.

**Ключевые концепции и аналогии.**

- Повторение жизненного цикла вызова «форма → серверный сервис → запрос → DTO → форма».
- Code review по принципам cohesion/coupling из TS и Node.
- Рефакторинг дублирования и имен, проверка экспортного API.

**Метаданные/артефакт FoodFactory.** Схема модулей и границ исполнения; очищенные `УтилитыFoodFactory`, `ПроверкиFoodFactory`, `СервисНоменклатурыFoodFactory`; чек-лист ручной проверки справочников.

**Самостоятельная практика.** С нуля реализовать небольшую форму подбора номенклатуры по требованиям, не копируя код дней 2–6, затем провести собственное ревью.

**Критерии готовности.** Не менее 80% пунктов контрольного списка выполнены без подсказки; нет необъяснённых клиент-серверных переходов; оставшиеся ошибки записаны как конкретные темы повторения. До 2 часов дня можно использовать как буфер.

**Недельная контрольная точка.** Ученик способен написать функцию, разместить её в обоснованном модуле, вызвать с клиента серверную выборку и безопасно показать результат. Если критерий не выполнен, день 8 начинается с оставшегося буфера, а не с форсированного продвижения.

## Неделя 2. Документы, регистры и оперативный контур

### День 8 — документы и приход сырья (7 ч)

**Цель.** Понять документ как факт хозяйственной операции и контейнер данных, пока без движений.

**Ключевые концепции и аналогии.**

- Документ, ссылка, объект, номер, дата, табличная часть; аналог aggregate root/event command, а не просто SQL-строка.
- Запись и проведение — разные состояния; проведение не равно сохранению формы.
- Обработчики заполнения, проверки перед записью и проведения имеют разные обязанности.
- Проверки на форме улучшают UX, но критические инварианты должны проверяться на сервере.

**Метаданные/артефакт FoodFactory.** Учебные справочник `Контрагенты` и документ `ПриходСырья` с реквизитами `Поставщик`, `Склад` и табличной частью `Материалы` (`Номенклатура`, `Количество`, `Цена`, `Сумма`).

**Самостоятельная практика.** Спроектировать форму и серверные проверки прихода: положительные количество/цена, только сырьё, отсутствие пустых ссылок, расчёт суммы без доверия к форме.

**Критерии готовности.** Документ записывается, некорректные строки отклоняются, итог пересчитывается; проведение пока либо отключено, либо не создаёт движений; место каждой проверки обосновано.

### День 9 — регистр накопления и движения прихода (7 ч)

**Цель.** Освоить регистр накопления остатков и впервые провести документ.

**Ключевые концепции и аналогии.**

- Измерения, ресурсы, регистратор и период; это не обычная ORM-таблица и не место для произвольного CRUD.
- Набор записей и движения документа; платформа связывает записи с регистратором.
- Виртуальная таблица остатков как предметный read model, а не вручную поддерживаемое поле `Остаток`.
- Запись движений должна быть воспроизводима при перепроведении.

**Метаданные/артефакт FoodFactory.** Учебный регистр накопления остатков `ОстаткиНоменклатуры`: измерения `Склад`, `Номенклатура`; ресурсы `Количество`, `Сумма`; движения прихода документа `ПриходСырья`.

**Самостоятельная практика.** Реализовать движения прихода и отдельный серверный запрос остатков на дату. Проверить изменение количества и суммы после изменения и перепроведения документа.

**Критерии готовности.** Один документ создаёт ожидаемые движения; отмена проведения удаляет его влияние; перепроведение не удваивает остатки; запрос использует виртуальную таблицу регистра.

### День 10 — расход, контроль остатков и проведение (7 ч)

**Цель.** Научиться формировать расходные движения и контролировать бизнес-инвариант при проведении.

**Ключевые концепции и аналогии.**

- Приход/расход — вид движения регистра, а не знак, расставляемый случайно.
- Оперативное проведение и момент времени; контроль остатков должен учитывать движения текущего документа.
- Отказ от проведения и пользовательская диагностика по дефицитным позициям.
- Массовый запрос по всем строкам вместо N+1 запросов.

**Метаданные/артефакт FoodFactory.** Черновая учебная версия документа `ВыпускПродукции` с `СкладомМатериалов`, `СкладомПродукции` и табличной частью `Материалы`; расходные движения по `ОстаткиНоменклатуры`.

**Самостоятельная практика.** Реализовать пакетную проверку достаточности сырья и сформировать расходные движения; самостоятельно определить корректное поведение при повторяющейся номенклатуре в строках.

**Критерии готовности.** Нельзя провести документ с дефицитом; сообщение перечисляет дефицит; нет запроса в цикле; корректный документ расходует точное агрегированное количество.

### День 11 — транзакции, блокировки и конкуренция (7 ч)

**Цель.** Не допускать отрицательных остатков при конкурирующем проведении.

**Ключевые концепции и аналогии.**

- Транзакция проведения, атомарность и rollback; аналог SQL transaction/unit of work.
- Управляемые блокировки и пространство блокировки данных; блокировать ровно затрагиваемые ключи регистра.
- Race condition «прочитал остаток → другой сеанс списал → записал».
- Дедлоки, единый порядок захвата и короткая транзакция; нельзя лечить конкуренцию глобальной блокировкой.

**Метаданные/артефакт FoodFactory.** Доработанный обработчик проведения `ВыпускПродукции`; карта блокируемых данных `Склад + Номенклатура`; сценарий двух параллельных сеансов.

**Самостоятельная практика.** В двух сеансах воспроизвести конкурирующее списание одного остатка, затем добавить управляемую блокировку и повторить опыт. Зафиксировать наблюдения.

**Критерии готовности.** После гонки не возникает отрицательного остатка; один конфликтующий документ получает понятный отказ; несвязанные склады не блокируют друг друга; ученик объясняет границы транзакции. Особенности поведения обязательно проверяются на используемой файловой базе, без переноса неподтверждённых выводов на клиент-серверную СУБД.

### День 12 — рецептуры и выпуск продукции (7 ч)

**Цель.** Связать нормативный состав продукта с фактическим выпуском.

**Ключевые концепции и аналогии.**

- Периодический регистр сведений как историзируемая relation/read model; периодичность выбирается по реальной потребности.
- Рецептура как версия норматива, а не изменение задним числом старых документов.
- Заполнение по данным рецептуры и независимость записанного документа от будущей смены норматива.
- Серверное пакетное получение состава.

**Метаданные/артефакт FoodFactory.** Учебный справочник `Рецептуры`; регистр сведений `СоставРецептур` с измерениями `Рецептура`, `Продукция`, `Материал` и ресурсом `КоличествоНаЕдиницу`; доработанный `ВыпускПродукции` с продукцией и количеством выпуска.

**Критерии готовности.** Состав выбирается на дату документа; округление количества задано осознанно; выпуск создаёт расход сырья и приход готовой продукции; старый документ воспроизводим.

### День 13 — продажи и регистры оборотов (7 ч)

**Цель.** Реализовать упрощённую отгрузку с контролем готовой продукции и аналитикой продаж.

**Ключевые концепции и аналогии.**

- Регистр накопления оборотов для потока событий за период, остаточный регистр — для состояния на момент.
- Денежные ресурсы и количество; точность и округление задаются метаданными.
- Один документ может атомарно создавать движения в нескольких регистрах.
- Проведение должно быть идемпотентным относительно перепроведения.

**Метаданные/артефакт FoodFactory.** Учебный документ `РеализацияПродукции` с покупателем, складом и табличной частью продукции; регистр накопления оборотов `Продажи` с измерениями `Контрагент`, `Номенклатура` и ресурсами `Количество`, `Выручка`; расход по `ОстаткиНоменклатуры`.

**Самостоятельная практика.** Реализовать проведение реализации, пакетный контроль остатка и движения двух регистров; проверить изменение покупателя, цены и количества с перепроведением.

**Критерии готовности.** Отмена проведения убирает оба эффекта; перепроведение не дублирует обороты; при дефиците не остаётся частичных движений; суммы совпадают с документом.

### День 14 — контрольная точка 2 и сквозной сценарий (7 ч)

**Цель.** Проверить целостность контура «приход → выпуск → продажа» и оставить время на исправления.

**Ключевые концепции и аналогии.**

- Инварианты агрегатов, транзакционная граница и проекции регистров.

- Диагностика через регистратор вместо ручного исправления записей регистра.

**Метаданные/артефакт FoodFactory.** Набор учебных данных сквозного сценария; карта движений трёх документов; реестр найденных и исправленных дефектов.

**Критерии готовности.** Фактические остатки и обороты совпадают с ручным расчётом; нет прямой ручной правки регистра; все критические сценарии повторяемы. До 3 часов — буфер на ошибки дней 8–13.

**Недельная контрольная точка.** Ученик объясняет, почему документы и регистры не заменяют друг друга, умеет построить движения и защитить остаток от конкуренции. Непройденный конкурентный сценарий считается блокером для дальнейшего усложнения проведения.

## Неделя 3. Запросы, отчёты и эксплуатационная безопасность

**Ключевые концепции и аналогии.**

**Самостоятельная практика.** Одним пакетным запросом получить товары с остатком, выпуском и продажами за период, включая позиции без продаж; заранее описать гранулярность каждой таблицы.

**Критерии готовности.** Итоги не размножаются; пустые данные трактуются осознанно; период и склад — параметры; результат сверяется с ручным набором дня 14.

### День 16 — система компоновки данных и отчёт по остаткам (7 ч)

**Цель.** Создать пользовательский отчёт и понять разделение источника данных, настроек и представления.

**Ключевые концепции и аналогии.**

- Настройки пользователя не должны менять бизнес-источник.
- Проверка итогов отчёта независимым запросом.

**Метаданные/артефакт FoodFactory.** Учебный отчёт `ОстаткиНаСкладах` на СКД с параметром даты, отборами склада и вида номенклатуры, группировками по складу и номенклатуре.

**Самостоятельная практика.** Создать два варианта отчёта: детальный и сводный; добавить условное оформление дефицита по заданному пользователем порогу.

**Критерии готовности.** Оба варианта работают без изменения схемы; сумма детальных строк равна сводному итогу; пустой склад и дата обрабатываются предсказуемо.

### День 17 — стоимость запасов и валовая прибыль (7 ч)

**Цель.** Реализовать упрощённую, явно ограниченную модель фактической стоимости.

**Ключевые концепции и аналогии.**

- Количественный и стоимостной учёт; стоимость выпуска нельзя достоверно получить только из продажной цены.
- Учебный средний метод: стоимость списания рассчитывается из доступных количества и суммы до расхода.
- Регистры — материализованное состояние; восстановление последовательности и изменение задним числом влияют на результат.
- Денежная точность и округление — часть доменной модели.

**Метаданные/артефакт FoodFactory.** Учебный регистр накопления `ЗатратыНоменклатуры` с измерениями `ДокументВыпуска`, `Продукция`, ресурсом `Сумма`; стоимостные движения `ВыпускПродукции`; отчёт `ПродажиИВаловаяПрибыль`.

**Самостоятельная практика.** Рассчитать учебную фактическую стоимость сырья выпуска и валовую прибыль продаж; исследовать последствия прихода задним числом и сформулировать ограничения алгоритма.

**Критерии готовности.** Ручной пример сходится до установленной точности; нулевой остаток не вызывает деления на ноль; ограничения среднего метода и задних дат явно записаны; результат не называется бухгалтерским учётом.

### День 18 — роли и права (7 ч)

**Цель.** Реализовать минимально необходимые права и проверить их отдельными пользователями.

**Ключевые концепции и аналогии.**

- Принцип least privilege; интерфейсная невидимость не заменяет запрет доступа.
- Права на чтение, добавление, изменение, удаление, проведение и интерактивные операции.
- Ограничение доступа на уровне записей — отдельный сложный механизм; не добавлять его без обоснованного требования и проверки влияния на запросы.

**Метаданные/артефакт FoodFactory.** Учебные роли `КладовщикFoodFactory`, `МастерПроизводстваFoodFactory`, `МенеджерПродажFoodFactory`, `АдминистраторFoodFactory`; тестовые пользователи для каждой роли; матрица доступа.

**Критерии готовности.** Запрет подтверждён не только отсутствием команды, но и фактической невозможностью операции; проведение доступно только нужной роли; матрица совпадает с результатами.

**Самостоятельная практика.** Реализовать команду без изменения основной конфигурации; отключить расширение и доказать, что основной контур продолжает работать; затем изменить форму основной конфигурации и проверить совместимость.

**Критерии готовности.** Расширение подключается и удаляется обратимо; основное проведение не перехвачено без нужды; заимствовано минимальное число объектов; риски документированы.

**Цель.** Системно локализовать ошибки и превратить ключевые сценарии в повторяемые проверки.

**Ключевые концепции и аналогии.**

**Критерии готовности.** Дефект воспроизводится до исправления и исчезает после; проверка ловит регрессию; в журнале нет чувствительных данных; этап локализации объяснён фактами.

**Метаданные/артефакт FoodFactory.** Набор увеличенных учебных данных; таблица замеров «до/после» для одного медленного сценария; контрольный сквозной прогон; список технического долга.

**Метаданные/артефакт FoodFactory.** Учебный отчёт `ПланФактРасходаСырья`; обновлённые роли и матрица доступа; набор регрессионных сценариев трёх отчётов.

**Самостоятельная практика.** Сопоставить норматив рецептуры с фактом расхода выпуска, добавить расшифровку до документа и проверить отчёт под каждой ролью, включая попытку открыть запрещённый документ.

**Критерии готовности.** План и факт сверены на ручном примере; расшифровка не обходит права; новые объекты явно включены или исключены в каждой роли; отчёты сходятся с регистрами.

### День 26 — итоговая задача: проектирование (7 ч)

**Цель.** Самостоятельно спроектировать небольшое законченное изменение без готового решения.

**Итоговая постановка.** Добавить в FoodFactory учебный сценарий «заказ на производство»: мастер фиксирует план выпуска на дату, система рассчитывает потребность в сырье по версии рецептуры, показывает дефицит по складу, а после фактического выпуска отчёт отражает план/факт. Заказ не должен сам создавать складские движения.

**Ключевые концепции и аналогии.**

- Требования → инварианты → модель данных → транзакции → права → проверки; аналог technical design перед реализацией.
- Command (`ЗаказНаПроизводство`) отделён от факта (`ВыпускПродукции`) и read model отчёта.
- Версионирование рецептуры, дата потребности, пакетный расчёт и гонки чтения.
- Критерии приёмки должны быть проверяемыми, а не «работает корректно».

**Метаданные/артефакт FoodFactory.** Проект нового учебного документа `ЗаказНаПроизводство`; проект регистра сведений `ПотребностиПроизводства` либо обоснованный отказ от него; схема связей, матрица прав, перечень модулей и план миграции.

**Самостоятельная практика.** Без реализации подготовить два варианта модели, сравнить дублирование, историчность и стоимость запросов; выбрать один и составить сценарии приёмки и отката.

**Критерии готовности.** У каждого реквизита есть назначение; явно указано, где код исполняется; движения или их отсутствие обоснованы; учтены права, блокировки, расширяемость и негативные сценарии.

### День 27 — итоговая задача: реализация и усиление (7 ч)

**Цель.** Реализовать выбранный дизайн вертикальным срезом и подтвердить его проверками.

**Ключевые концепции и аналогии.**

- Вертикальный срез: метаданные, серверная логика, запрос, форма, права и проверка вместе.
- Малые коммиты/версии конфигурации и обратимые изменения.
- Batch query вместо циклов, инварианты на сервере, тонкая форма.
- Наблюдаемость ошибок и воспроизводимость тестовых данных.

**Метаданные/артефакт FoodFactory.** Учебный `ЗаказНаПроизводство`, выбранное хранилище потребностей, связь с `ВыпускПродукции`, форма расчёта дефицита, права и проверки; краткий журнал решений.

**Самостоятельная практика.** Реализовать задачу по собственному проекту дня 26. Наставник проверяет постановку, но не выдаёт готовые модули.

**Критерии готовности.** Happy path и минимум пять негативных сценариев проходят; заказ не меняет склад; потребность воспроизводима на дату; нет N+1; запрещённая роль не проводит и не видит недоступные данные; изменения можно откатить.

### День 28 — приёмка, повторение и буфер (7 ч)

**Цель.** Провести техническую приёмку FoodFactory, закрыть критические пробелы и определить следующий этап обучения.

**Ключевые концепции и аналогии.**

- Приёмка по трассе «требование → метаданные → код → данные регистра → отчёт → право → тест».
- Ретроспектива ошибок и интервальное повторение: язык, модули, запросы, проведение, транзакции, клиент-сервер.
- Классификация долга: correctness, security, performance, maintainability.
- Definition of Done не равен отсутствию видимой ошибки.

**Метаданные/артефакт FoodFactory.** Приёмочный чек-лист; демонстрационный набор данных; архитектурная схема; список известных ограничений; backlog следующего этапа.

**Самостоятельная практика.** За ограниченное время восстановить чистый демонстрационный сценарий от прихода до план/факта, объяснить архитектуру без подсказок, исправить один найденный критический дефект и повторить регрессию.

**Критерии готовности.** Сквозной сценарий повторяем; остатки и отчёты сверены; права проверены отдельными пользователями; конкурентное списание безопасно; итоговая задача принята по критериям дня 26. До 3 часов сохраняются как буфер — на исправление, повторение или документацию, но не на новую функцию.

**Финальная контрольная точка.** Ученик самостоятельно реализует небольшой оперативный контур в новой учебной конфигурации, умеет объяснить размещение кода и подтвердить результат данными, запросом и проверочным сценарием.
